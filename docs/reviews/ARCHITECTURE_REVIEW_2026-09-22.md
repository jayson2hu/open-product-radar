审查日期：2026-09-22。范围：独立 worker、采集调度、趋势窗口、邮件投递、采集报告、备份恢复及已有容器配置。本轮未运行真实采集、未改实采数据库、未外发邮件、未安装或启动 Docker。

## 结论

现有模块化单体适合作为单机试点：网页读取已存储结果，长耗时采集在独立进程，SQLite WAL、来源权限、任务租约、请求预算及审核状态均有实际实现。当前仍是本机 Node.js 运行；容器配置不等于容器实测通过。没有持续多日观测或实际运行记录，不能由一次成功采集推断持续调度、趋势榜稳定性或生产 SLA 已达标。

## 本轮已修复的问题

| 优先级 | 原问题 | 最终行为与回归覆盖 |
|---|---|---|
| P1 | 最后一次执行崩溃，attempts 已到 5；租约过期后永久留在 running 且无法领取 | 领取任务时清理已耗尽且无有效租约的任务，标记可观察的失败；有效租约不误杀 |
| P1 | 人工重试将 attempts 重置后，复用旧预算记录 ID，漏记新执行预算 | 每次领取产生独立租约标识；预算按执行租约幂等，同一执行不重扣，新执行重新预留 |
| P1 | release 证据删除后，重新采集虽不重新建证据，原始 HTTP 缓存仍可能写回已删除原文 | 缓存写入事务再次检查删除台账；含被删除证据的响应不落缓存，已有对应缓存清除 |
| P1 | 旧执行者失去租约后，错误清理再次抛异常，干扰新的执行者状态 | 只有当前租约所有者可结束任务；旧执行返回 LEASE_LOST，不覆盖替代执行 |
| P1 | 多引用事件只要求任一引用有效，另一出处撤销后仍可能邮件发送整段摘要 | 准备摘要和发送前均要求整组引用有效；任一来源撤销则整条事件停止投递 |
| P2 | 本机采集报告展示所有历史失败，可能把已恢复的仓库继续标为失败 | 复用各仓库最新任务窗口的状态投影；历史失败仍留在任务台账 |
| P2 | 外部 JSON 删除台账没有 demo/production 模式校验；备份文件未明确 Unix 权限 | 台账包含 mode，恢复前必须匹配备份；新 SQLite 备份设为 0600，Windows 访问仍由 ACL 管理 |

## 调度、窗口与 304 的准确含义

调度按 6 小时窗口为同一仓库生成唯一任务，主循环默认每 30 秒检查待处理任务；这是“轮询频率”和“采集频率”两个不同数值。默认每个请求最多 30 秒，本机单次实采脚本默认 45 秒，允许范围为 1～45 秒。仓库元数据与 releases 顺序请求，两次上限为 90 秒，低于默认 120 秒租约；长尾、暂停和进程崩溃仍由租约及重试处理。

24 小时净变化只接受实际间隔 23～25 小时的同实体、同来源、同指标和同范围快照；7 天为 167～169 小时。负数保留，零基数无增长率，缺基准不补零。6 小时采样不能保证任意时刻都有合格基准：首次运行可能不在固定窗口边界，之后任务失败或延迟也会使间隔不合格。应显示历史不足或区间不可比，不扩宽口径伪造连续趋势。

304 表示官方 API 确认缓存资源未变更，已有有效缓存时可生成本次观测快照；同计数在满足时间窗口后得到 0 净变化。304 不是请求失败，也不意味着新 release 已审核。没有缓存的 304 会报错。第一次成功采集通常只有一个时间点；今天发现历史 release 不等于今天发布。

## 数据和投递边界

仓库稳定身份使用 GitHub 数字 ID。公开仓库元数据可进入展示，release 与证据保持待审；采集不执行仓库代码、不自动推断产品关系、不因重试重复发布事件。失败不会写零覆盖最后有效计数。

HTTP 缓存条数是按地址去重的缓存数量，不是精确 HTTP 请求次数；预算预留也不是实际成功响应数。本机报告保留兼容字段 request_count，并明确 request_count_basis，同时提供 cached_endpoint_count 与 request_budget_reserved。精确网络请求计数仍未独立埋点。

人工和定时摘要共用事件版本台账。发送前重查用户订阅、关注状态、事件版本及所有引用；空摘要不发送。供应商响应不确定时保留 uncertain，禁止盲目重发。已发邮件无法召回；重大更正仍需运营核查。每日/每周分组目前采用 UTC 日界，应在明确本地时区需求后独立完善，不能声称已有按用户时区的发信时刻编排。

来源暂停保留历史供阅读；自动邮件采用更保守规则，仅使用当前仍允许的来源。开启来源不等于 worker 正在持续运行，网页健康也不等于采集成功。来源授权当前仍需要人工核查用途和保存范围，不是自动法律判断。

## 备份兼容性与生产前条件

新导出的独立删除台账必须包含 `mode: "demo"` 或 `mode: "production"`，并与备份一致。旧的无 mode JSON 台账不能直接用于恢复：应从对应当前数据库重新导出，或使用 `--current` 读取同模式当前库。恢复只写新目标，校验备份及最新删除台账，失效会话和可能重复的投递队列；不会自动删除原库。

备份、删除台账及邮件预览包含敏感资料，需要操作系统访问控制和受控保留。当前并未建立自动异地备份、数据库加密、容灾切换或生产 RPO/RTO 保证；本机恢复测试不能代替目标部署环境演练。

Docker/Compose 已具备固定镜像版本、非 root 用户、独立命名卷、本机端口绑定、网页健康检查、显式 worker profile 和预算/超时参数；worker 不继承网页 HTTP 探针，默认只入邮件队列。当前机器没有可用 Docker，不重复探测，也未声称 compose config、镜像构建或容器健康已验证。参见 `docs/CONTAINERS.md` 及容器核查产物。

本轮保持单机试点范围。PostgreSQL、多实例写入、自动扩缩容、完整外部可观测平台、真实 OAuth 和邮件供应商验收仍需对应环境完成，不能由本次源码审查替代。
