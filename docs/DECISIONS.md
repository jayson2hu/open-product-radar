# 实施决策

## ADR-001：先交付可运行的单机试点

原方案的 Python/FastAPI、PostgreSQL、Nuxt 是建议。当前机器已具备 Node.js 24，而默认 Python 是 3.7。首版采用 Node.js 24 原生 HTTP/SQLite、React 19、Vite 的模块化单体，减少本地启动依赖。网页与采集独立进程，页面读取已存储结果。具体版本由 package-lock.json 锁定。

这不是宣称 SQLite 可满足任意生产规模：单机试点使用 WAL、约束、事务和迁移；不部署多个写入副本或跨网络文件系统。多人运营和高并发前迁移 PostgreSQL，并重测租约、备份、事务、分页与隔离。原方案的 1,000 实体/10 万观察/20 并发性能目标未因技术选型而自动成立。

## ADR-002：演示与实采彻底分库

默认 demo 数据库提供明确标识的合成样例，名称及出处用于演示研究结构，指标、事件、结论不是已核查事实。production 从空数据开始。数据库自身记录 mode，应用拒绝混用。真实数据采集成功也不将种子样例改称实采。

## ADR-003：认证与外发分开

演示账户只用于本地试用，服务端仍按用户隔离私有资料。生产使用 GitHub OAuth 的公开身份，不申请私有仓库权限。没有 OAuth 配置时显示配置缺失，不能降级为演示登录。邮件订阅独立授权；邮件默认仅预览，不在开发过程中向任何人发送消息。

## ADR-004：事实发布以证据和人工审核为门槛

仓库公开 API 数据可保存原始观测；版本和产品变化进入审核。未知与不支持分开，云版与本地版分开，不计算综合潜力分，不从 Star 推断收入。不运行被收录代码。首版没有启用模型服务，不假装已经接入 AI 自动研究。

## ADR-005：先验证窄任务

首批结构样例只围绕浏览器自动化。首版不引入社区、自动扣款、全网爬虫或无限人工研究。付款支持运营人工核对后记录，不能把演示订单当作收入。访谈、试用、支付与续费结果从零开始记录。

## ADR-006：部署与经营的交付边界

本地运行、自动测试、部署材料和运营模板属于本次开发交付。域名、真实账号、发信服务、主体条款和公开部署需要实际配置与核查。没有进行外部发布、购买服务、招募、代收款或发送营销消息。
